# Технические требования

## Подход и стек

Приложение работает на стороне клиента и публикуется как статический сайт. Собственного сервера, API, аккаунтов и серверной базы данных нет.

- **React** — интерфейс и управление состоянием.
- **TypeScript** — типизация кода; строгий режим включён. Данные из внешних источников, включая хранилище браузера, проверяются во время выполнения: типы сами по себе не гарантируют их корректность.
- **Vite** — локальная разработка и сборка статического приложения. Использовать официальный шаблон React с TypeScript как отправную точку.
- **Node.js 26.12.1 и nvm** — версия Node.js зафиксирована в `.nvmrc`; использовать `nvm use` в корне проекта. Это последняя из версий, установленных через nvm на момент выбора. Совместимость с зависимостями проверить при инициализации.
- **Yarn** — установка зависимостей; хранить `yarn.lock` в проекте. При инициализации зафиксировать версию Yarn в `packageManager` и описать её подключение в README.
- **Tailwind CSS** — стили интерфейса с интеграцией через официальный плагин Vite. Общие дизайн-токены и необходимые базовые стили определять централизованно; CSS Modules не использовать. Библиотеку компонентов не добавлять без конкретной необходимости.
- **ESLint и Prettier** — единые правила кода и форматирования; проверка типов выполняется отдельно от сборки Vite.
- **Vitest и React Testing Library** — проверка ключевой логики и пользовательских сценариев. Инструмент для браузерных end-to-end тестов добавлять только при появлении обоснованной потребности.

Использовать актуальные стабильные совместимые версии на момент инициализации. Дополнительные зависимости вводить только при ясной пользе; не добавлять глобальный менеджер состояния заранее, если достаточно средств React. Для согласованных маршрутов выбрать наиболее простую подходящую реализацию навигации.

## Архитектура

Организовать код по предметным областям и ответственности, без обязательных пустых слоёв. Начальная структура — ориентир, который можно уточнить при реализации:

```text
src/
  app/          # запуск, корневой компонент, общая композиция
  features/
    tasks/      # модель задачи, операции, список и формы
    calendar/   # представление задач по дням и времени
    reminders/  # управление напоминаниями и возможности браузера
    onboarding/ # приветственный экран
  shared/       # действительно общие UI-компоненты и утилиты
  styles/       # глобальные стили и переменные дизайна
```

- Модель задачи и правила операций находятся в `tasks`; календарь и остальные представления используют те же задачи. Отдельной модели событий нет.
- Вычисления и правила, не зависящие от интерфейса или браузера, отделять от React-компонентов. Компоненты отвечают за отображение и взаимодействие; работу с браузерными API изолировать за небольшими адаптерами.
- Состояние задач имеет один источник истины в приложении. Начать со встроенных средств React; вычисляемые списки и прогресс получать из задач, не хранить их как независимые данные.
- Хранилище, напоминания и представления не должны зависеть от внутренней реализации друг друга. Общий код выносить только при реальном повторном использовании; не создавать универсальные абстракции про запас.
- Локальное состояние интерфейса держать рядом с компонентами, которым оно нужно. Границы и имена модулей должны помогать новому разработчику быстро понять проект.

## Маршрутизация и переходы

Реализовать маршруты и поведение навигации, описанные в [функциональности](features.md#экраны-и-маршруты): прямые ссылки, параметры, обновление страницы, историю и закрытие контекстной формы кнопкой «Назад». Для статического хостинга настроить возврат приложения на клиентских маршрутах; если хостинг этого не поддерживает, выбрать совместимый вариант маршрутизации и отразить его в документации.

Плавные переходы и обратная связь обязательны с учётом [визуального направления](design.md#состояния-и-движение), производительности и настройки уменьшения движения. Начать с возможностей CSS и браузера; библиотеку анимации добавлять при подтверждённой необходимости. Контекстные формы должны сохранять доступность, управлять фокусом и не нарушать работу навигации.

## Данные и хранение

Использовать `localStorage` для задач и небольших настроек, включая признак прохождения приветственного экрана. Данные сохраняются между сеансами в пределах одного браузера и origin; синхронизации между устройствами нет. Очистка данных сайта или недоступность хранилища может привести к потере данных.

- Хранить задачи с устойчивыми идентификаторами и явным состоянием, включая удаление и восстановление. Завершённые и удалённые задачи должны сохраняться после перезагрузки.
- Хранить версию формата данных; при изменении схемы предусматривать миграцию. Проверять считанные данные и обрабатывать ошибки чтения, записи и некорректный формат без незаметной перезаписи пользовательских данных. При неудачном сохранении явно сообщать об этом пользователю.
- Определить и единообразно применять правила дат, локального времени, смены дня и часового пояса; дата без времени не должна превращаться в задачу с вымышленным временем.
- Учесть несколько открытых вкладок: изменения не должны молча перезаписывать более новые данные. Конкретный механизм согласования определить и проверить при реализации.

## Напоминания и ограничения браузера

Напоминания зависят от поддержки браузера, разрешения пользователя и условий работы приложения. HTTPS необходим там, где того требуют браузерные API; локальная разработка может использовать возможности localhost. Проверять доступность API и разрешение, понятно показывать отказ или неподдерживаемый сценарий.

Без сервера и внешней службы нельзя исходить из гарантированной доставки точно в срок, особенно когда приложение закрыто или работа вкладки приостановлена. Service worker сам по себе не гарантирует пробуждение в заданный момент; периодическая фоновая синхронизация поддерживается ограниченно и не обеспечивает точного расписания. До реализации проверить целевые браузеры и устройства и согласовать фактически поддерживаемое поведение, включая напоминания после срока. Не выдавать ограниченную реализацию за гарантированную фоновую доставку.

## Качество и соглашения

- Писать читаемый код с понятными именами, небольшими связанными модулями и единообразными паттернами. Избегать дублирования правил и сложных абстракций без необходимости.
- По умолчанию использовать семантические HTML-элементы; поддерживать клавиатуру, видимый фокус, доступные названия элементов и уменьшение движения. Проверять контраст, мобильные и десктопные размеры.
- Обрабатывать пустые и ошибочные состояния и не скрывать сбои сохранения. Не хранить секреты в клиентском коде или браузерном хранилище.
- Проверять типы, линтер, форматирование и production-сборку. Тестировать существенную логику задач, дат и хранения, а также ключевые пользовательские сценарии; не писать тесты только ради покрытия.
- После инициализации проекта описать в README требования к окружению и команды установки, запуска, сборки и проверки. При значимых изменениях поддерживать документацию в актуальном состоянии.
- История Git: отдельные логически завершённые изменения и сообщения в формате Conventional Commits, как описано в концепции проекта.

## Что уточнить при реализации

- Целевые версии браузеров и фактические ограничения уведомлений на них.
- Правила дат и часовых поясов, стратегию согласования вкладок и восстановления после ошибок хранения.
- Какую реализацию маршрутизации и при необходимости библиотеки для дат, календаря или анимации выбрать с учётом реальных требований.

## Принятые решения реализации

- Даты и время — локальные календарные значения без преобразования в UTC; при смене часового пояса сохраняются введённые значения. День пересчитывается при работе приложения.
- Хранилище версионировано; данные проверяются перед использованием. Запись проверяет ревизию, а изменения из других вкладок принимаются через событие `storage`. При конфликте открытой формы требуется открыть её заново.
- Навигация использует History API; статическому хостингу необходим fallback на `index.html`.
- Напоминание однократно показывается при наступлении времени, пока приложение открыто; возможна задержка при приостановке вкладки. Это ограничение согласовано для первого этапа. Повторных напоминаний нет.
- Удалённые задачи хранятся до окончательного удаления пользователем; автоматического срока хранения нет.
- Tailwind подключён без Preflight: макеты используют стандартные стили типографики браузера, а общие прикладные стили заданы отдельно. Утилиты и тема Tailwind остаются доступны.
